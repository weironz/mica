# 容灾方案（DR）— 现状实测、恢复路径、以及为什么不做双活

> 2026-07-30 首版。全部数字来自当天在生产节点 `mica.cloudcele.com` 的实测，
> 每条都标了取证方式，好让下一个人能复核而不是继承信念。
>
> 本文只管**灾难恢复**（数据没了怎么找回来）。日常备份的**机制**说明在
> `docs/backup.md`，恢复 runbook 也在那里；本文管的是**策略**：备了什么、丢多少、
> 多久能起来、哪条路没人走过。

## 0. 一句话结论

**（2026-07-30 当天已改变）** 现在内容与数据库**都**每天异地一份。本文最初写下时
数据库异地一份都没有 —— 那个洞当天就补上了（5.0），过程与取证留在下面，因为它是
本文存在的理由，也是「机制写好了但没人接线」这类失败的标本。

> 🔴 **2026-08-29:上面这句「每日」曾经连续 13 天是假的。** 详见第 8 节 ——
> 那次事故的价值不在于修好了什么,而在于它证明了**这份文档里的 ✅ 会腐烂**,
> 而且腐烂时不会有任何人被通知。读到任何一个 ✅,先问「最后一次核实是什么时候」。

**当前状态**：
- ✅ **数据库**：每日 `pg_dump` → rustic `label=_pgdump` → 阿里云 OSS
  （**2026-08-16 ~ 08-29 中断,见第 8 节**）
- ✅ **内容（正文+图片）**：每日导出 → 每工作区一个 label → 同一仓库
- ✅ **对象字节**：0.13.8 起 rclone 直传 OSS（`mica-blobs` 前缀），不再只靠导出间接捞
- ⏸️ **跨账号第二份**：**已拍板不做**（用户判断云账号级损失概率足够低）
- ✅ **凭据**：`RUSTIC_PASSWORD` 已由用户单独留存于节点之外

**仍然没有答案的一件事**：RTO。恢复路径现在**存在**了，但端到端「换台机器把服务起回来」
这条路**没有人走过**，所以「多久能恢复」目前只有猜测（5.5）。

**双活不做**（第 6 节存档理由）。要提可用性，正确的下一档是 warm standby。

## 1. 今天实测到的事实

| 事实 | 取证 |
| --- | --- |
| 每日备份**跳过了 pg_dump** | 备份容器日志原文：`WARN: MICA_BACKUP_PGURL unset — skipping pg_dump (content-only backup, no DB disaster recovery)` |
| 异地仓库里**从来没有过** DB 快照 | `rustic snapshots --filter-label _pgdump` → `total: 0 snapshot(s)`（全仓 170 个快照） |
| 节点 `.env` 缺 `MICA_BACKUP_PGURL` | `grep -E '^(MICA_BACKUP|OSS_|BACKUP_)' /data/mica/.env` —— 有 TOKEN / PASSWORD / OSS_* / BACKUP_HOUR，**无 PGURL** |
| 内容备份是好的 | 同一次运行 `snapshotted 22 workspace(s)`，导出含 **Markdown + 图片** |
| DB 的唯一副本在**节点自己的盘上** | `/data/mica/pre-*.sql.gz` 共 5 个手工还原点，最新 `pre-0.13.5-20260730-164652.sql.gz` |
| 异地仓库与节点**同一个云账号** | rustic → `opendal:s3` → 阿里云 OSS；ECS 也在阿里云 |
| 仓库自身完整性 OK | `rustic check` 170 snapshot 全过（2026-07-30） |
| 恢复演练走过一次 | `just restore-drill`：错误 0、`_sqlx_migrations`=15、**3331 可读页**、32 FK / 19 PK |

### 1.1 为什么这个洞能活这么久

**死人开关对它是绿的。** `mica-backup-loop.sh` 在运行**成功**时 ping healthchecks.io ——
而「跳过 pg_dump」是一次**成功的运行**：脚本按设计降级、打一条 WARN、继续把内容备完、
正常退出。监控能抓住「备份没跑」，抓不住「备份少备了一半」。没人读备份日志，WARN 就等于没写。

同一形状在 `lessons.md` 里反复出现：**降级路径必须让人看见，否则它就是静默失败**。

## 2. 备了什么 / 没备什么

内容导出（`mica-cli export`，每日 → OSS）覆盖的：

- 22 个工作区的页面正文（Markdown）
- 页面里的图片（导出即含，**不是**只有 DB 里的引用）

**不覆盖**的（这些只存在于 Postgres，而 Postgres 没有异地副本）：

- 账号与口令 hash、邮箱验证状态
- workspace 成员关系与角色（谁能看谁的东西）
- **CRDT 编辑历史**（`document_yrs_base` 的 state）—— 导出是当前正文的投影，不含历史
- 版本检查点（`document_yrs_versions`，含用户命名的检查点）
- **评论**（`comment_threads` / `comments`，锚点存在独立表，正文里一个字都没有）
- 分享 token（公开链接会全部失效）
- refresh tokens（所有人被登出，可接受）
- 回收站内容（导出过滤 `is_deleted=false`）

一句话：**导出救得回「文字和图片」，救不回「这是谁的、谁改过、谁评论过」。**

### 2.1 分类：两类数据源 + 一类凭据，Markdown 导出不在其中

容易搞错的一点：**Markdown 导出不是「要备份的东西」，它是当前唯一在跑的备份手段**（一个有损投影）。
真正持有状态的是节点上的卷，而其中只有两个算数据源：

> 下表的「异地现状」是 **2026-07-30 当时**的快照,两格都已在之后修复 —— 当前状态看第 0 节。

| 卷 | 装什么 | 要不要备 | 异地现状(2026-07-30) |
| --- | --- | --- | --- |
| `mica-prod-postgres` | 一切关系型状态（账号 / 关系 / CRDT / 版本 / 评论 / 分享 token） | ✅ **要** | 🔴 **没有** —— `MICA_BACKUP_PGURL` 未设 |
| `mica-prod-rustfs` | 图片字节 | ✅ **要** | 🟡 **间接**：只靠导出里的图片 |
| `mica-prod-backup` | 导出暂存区 `/var/lib/mica/export` | ❌ 派生产物 | — |

**图片那格是「间接」不是「有」**：没有任何东西直接备 `mica-prod-rustfs`，图片能回来纯粹因为导出把
它们一起写出去了。这意味着覆盖范围由**导出规则**（`is_deleted=false`）决定，而不由盘上有什么决定 ——
孤儿 blob 与回收站页面独有的图片都不在。要覆盖完整，得直接备那个卷，或者接受这个边界并写明。

> **`content` 那条腿的还原状态(2026-08-30 查实)**:分两段。**第一段已验证** ——
> 从仓库里取出一个工作区谱系,得到的是原样的目录树、层级、中文文件名和可读 Markdown。
> **第二段从没走过** ——「把这棵树变回 Mica 的工作区」:导入端点吃的是 **zip 不是目录**
> (`read_zip`,单次上限 256 MiB),而且它是**通用 Markdown 导入器,不是 round-trip 还原**:
> 页面 id、CRDT 历史、评论、分享链接、账号与成员关系**都不会回来**(那些只在数据库里),
> 导进去的是**文字相同的新页面**。
>
> 所以这条腿不是实例恢复路径 —— 实例恢复是数据库 + 对象(已端到端验证)。它是
> 「不依赖 Mica 也能读自己的笔记」+「数据库彻底没救时的最后手段」。细节见
> [`backup.md`](backup.md)。

### 2.2 第三类:凭据(不备这类,前两类备得再好也白搭)—— **已修,v0.13.40**

节点 `/data/mica/.env.secrets`,里面有 `POSTGRES_PASSWORD`、JWT secret、S3 / RustFS keys、
邮件 AK、`MICA_BACKUP_TOKEN`,以及 **`RUSTIC_PASSWORD`**。

~~**它现在哪儿都没备,且与数据同一块盘。**~~ 这一条从 2026-07-30 写下起原样躺了一个月,
直到 **08-29 的演练把它变成了一堵墙**:重建出来的机器一路走到「栈起来了、是空的」,
然后**停在这里** —— 灌数据要凭据,而凭据只存在于一个人的密码管理器里。

**v0.13.40 起 `.env.secrets` 只读挂进 backup 容器,作为第四条 leg(`_config` lineage)
进备份**;没挂载则该 leg 记为 skipped,而 skipped **默认让整个 run 失败** —— 「凭据没备份」
必须响亮,不能是日志里一行没人看的话。

**有三样它解不掉,而且不可能解掉。** 打开这个仓库需要:

```
MICA_BACKUP_PASSWORD          # rustic 的仓库口令
OSS_ACCESS_KEY_ID             # 连得上 OSS 才读得到仓库
OSS_SECRET_ACCESS_KEY
```

> **这三个是节点上的环境变量名。** 在 GitHub Secrets 里,后两个存的是
> **`ALICLOUD_ACCESS_KEY` / `ALICLOUD_SECRET_KEY`** —— 因为这台装机上它就是同一把
> 阿里云 key(既开机器、也读桶),给同一把钥匙起两个名字本身就是"乱"的来源。
> **代价要说清**:于是**一把凭据既能读你全部数据、又能创建和销毁基础设施**。
> `backup.md` 仍然推荐给备份角色单独开一把桶级最小权限的 RAM key —— 那是更好的
> 形态,现在这个是明确选择,不是默认。

这三个**全都在这个文件里**,而这个文件在仓库里。**保险柜的密码锁在保险柜里。**
所以它们仍然必须被带在外面 —— 但**只剩这三个**,不是十三个。

〔第一版这里写的是「只剩一个」,漏了 OSS 那对:只想到 rustic 的加密口令,没想到
"连得上"本身也要凭据。这正是 §9 那类前提 —— **在真跑一遍之前,它看起来是成立的**。〕

**带在哪(2026-08-29,用户拍板)**:GitHub Secrets。好处是恢复链路上**不需要人**;
代价说清楚 —— **持有那个仓库的人就持有数据**。这与 §7.2 里「不防账号级风险」是同一档
取舍,不是新开的口子,但它把"账号"从阿里云一家扩到了两家。

> 想把三个降回一个,唯一干净的办法是**给 DR 实例挂一个 OSS 只读的 RAM 角色** ——
> 机器凭身份读桶,不带 key。今天不做:它要改 tofu、改 rustic 的凭据来源,而收益
> 是"少存两个 Secret"。**先记着,别现在做。**

> **有一样刻意不在这三层里**:`TRAEFIK_BASIC_AUTH`(Traefik 面板的 basic auth)。
> 它守的是个面板不是数据、`htpasswd -nbB` 一条命令就能重生、丢了立刻可见(登不进去)。
> 曾经把它塞进 `.env.secrets` 让备份带上,当天就退回来了 —— 那个文件是 **mica 栈**的,
> 由 `docker compose --env-file` 消费、`environment:` 是显式允许清单,而 Traefik 是
> 另一个栈。**真正的规则比「全都要进 git 或备份」窄:丢了找不回来、或者丢了没人知道的,
> 才必须进。** 重建出来的节点换一个新面板口令,代价到此为止。

**还原(必须在起栈之前)**。新机器上只有这个镜像,所以还原不能依赖已经跑起来的栈 ——
`mica-cli backup restore-config` 就是为这一刻加的(v0.13.41):

```bash
docker run --rm -v /data/mica:/restore --entrypoint /usr/local/bin/mica-cli   -e RUSTIC_PASSWORD -e OSS_BUCKET -e OSS_ENDPOINT -e OSS_REGION -e OSS_ROOT   -e OSS_ACCESS_KEY_ID -e OSS_SECRET_ACCESS_KEY   <registry>/mica-cli:<版本> backup restore-config
install -m 600 /data/mica/etc/mica/env.secrets /data/mica/.env.secrets
```

⚠️ **v0.13.41 上 `--entrypoint` 不能省**:那一版的 ENTRYPOINT 是整条
`mica-cli backup daemon`,不覆盖的话参数接在后面,拼成
`backup daemon backup restore-config`。**下一版起 ENTRYPOINT 只是二进制、
`CMD` 提供默认参数**,那时 `--entrypoint` 可有可无(留着也无害)。

> 做成命令而不是在文档里贴一段 `rustic.toml`:那些 repository 选项只有一种写法对
> (`enable_virtual_host_style` 是 OSS 必需的,当初是踩出来的),抄一份进 runbook 就是
> 第二处表示,会和 `render_rustic_conf` 悄悄漂移。

⚠️ **顺序是硬的**:`POSTGRES_PASSWORD` 在这个文件里,而 postgres 用它 initdb。
先起栈再还原凭据 = 库是用旧口令建的、配置写着新口令,谁都连不上。

### 2.3 Traefik / ACME 证书（2026-07-30 查实）

- **Traefik 不在 mica 的 compose 里。** compose 第 218 行那个 `traefik:` 是 `networks:` 段的
  `external: true` 网络（`traefik-network`），**不是 service**。反代是独立的一套栈
  （容器 `traefik-traefik-1`），印证 roadmap 那句「Traefik 配置本体在仓库外未纳管」。
- **证书是持久化的**：`traefik_traefik-certificates/_data → /etc/traefik/acme`，重启不丢。
- **但它不在任何 mica 备份里**（属于另一套栈的卷）。份量轻：丢了可重新签发，只需注意
  Let's Encrypt 的频率限制。真正的残留仍是**配置本体没纳管**。

### 2.4 别把邻居的备份当成自己的（2026-07-30 查实）

同一台节点上还跑着一套无关的 `neostor-*` 栈，里面有 `neostor-pgbackup-1`
（`prodrigestivill/postgres-backup-local:16`，`@daily`）和 `neostor-oss-offsite-1`
（rclone `sync /backups oss-crypt:`）。**它们不覆盖 mica**：那个 pgbackup 的
`POSTGRES_DB=neostor` / `POSTGRES_USER=neostor`，连的是它自己那套栈的 postgres。

记在这里是因为「机器上有个 pgbackup 容器在跑」很容易被下一个人（或未来的我）当成
"数据库有备份"。**mica 是这台机器上唯一没有自动异地 DB 备份的应用。**
顺带一句：邻居用 `postgres-backup-local` + rclone→OSS 把同一个问题解决了，而 mica 只差
一个已经写好的开关没打开（5.1）。

## 3. RPO / RTO

分两套算，因为它们的备份状况天差地别。

| | 内容（正文+图片） | 数据库（账号/关系/历史/评论） |
| --- | --- | --- |
| **RPO**（丢多少） | ≤ 24h（每日 `BACKUP_HOUR` 一次） | ≤ 24h（2026-07-30 起，同一节拍）<br>~~∞ —— 无异地副本~~ |
| 唯一副本位置 | 阿里云 OSS（异地，同账号） | 阿里云 OSS，`label=_pgdump`（同上，2026-07-30 起）<br>另有节点本地 `/data/mica/pre-*.sql.gz` 手工还原点 |
| 那份副本的新鲜度 | 每天 | 每天（本地还原点仍只在**发版前手工**落） |
| **RTO**（多久起来） | **11 分 50 秒**（2026-08-29,CI 无人值守实测） | **同一次恢复覆盖** |

**RTO:11 分 50 秒 —— 由 CI 无人值守跑出来的,不是人照着 runbook 走出来的。**

`.github/workflows/dr-drill.yml` 一次 `workflow_dispatch`:建机器 + DNS → provision →
从备份还原凭据 → 起栈 → 灌库 → 灌对象 → 断言 → **销毁**,全程无人。2026-08-29 首次
全绿的那一跑:

```
restored keys: 15
source 6467 objects / 1042495633 bytes; destination 6467 / 1042495633
{"status":"ok","version":"0.13.43"}
docs|nonempty|views|workspaces = 14882|14681|17800|32
Destroy complete! Resources: 11 destroyed.
```

**这个数字和「人照着文档走一遍」不是一回事,后者是下面这张表。** 两者都保留:出事那天
如果 CI 也够不着,走的就是下面那条。

**人工路径:≈ 10 分钟,2026-08-29 端到端实测。** 从零开一台阿里云 ECS 到浏览器里看见完整数据,
逐步实测(工作表 [`dr-drill.md`](dr-drill.md),每步都已标 `[已验证]`):

| 步骤 | 耗时 |
| --- | --- |
| 0 `tofu apply` 开机器(含 sshd 起来) | ~1 分钟 |
| 1 DNS 两条 A 记录(也归 tofu) | 秒级 |
| 2–3 `ansible/provision.yml`:docker + Traefik + 拉三个第三方镜像 | ~2 分钟 |
| 4 `mica-cli backup restore-config` 还原凭据 | **2 秒** |
| 5 `ansible/deploy.yml` 起栈 | 43 秒 |
| 6 取 `_pgdump`(634 MB)+ 灌进空库 | ~1 分钟 |
| 7 rclone 取回 6467 个对象 / 994 MiB | < 2 分钟 |
| 8 核验(浏览器,人工) | ~5 分钟 |

**时间花在哪(2026-08-29 实测)** —— 决定"要不要做并发"的依据:

| 恢复阶段 | 耗时 | | 备份阶段 | 耗时 |
| --- | --- | --- | --- | --- |
| 取 `_config` | 2 秒 | | **导出所有工作区(走 API)** | **3 分 54 秒** |
| 取 `_pgdump`(634 MB) | 9.2 秒 | | 32 个工作区打快照 | ~80 秒 |
| `psql` 灌库 | 16 秒 | | `pg_dump` | 17 秒 |
| 取回 6467 对象 / 994 MiB | < 2 分钟 | | dump 打快照 | 11.5 秒 |
| **数据合计** | **~2.5 分钟** | | **合计** | **~6.5 分钟** |

**结论:不做并发**,因为瓶颈不在能被并发解决的地方。

- **恢复**:数据搬运只占 RTO 的 2.5/10。大头是开机器+provision(~3 分钟)和人工
  核验(~5 分钟)。而两条显而易见的提速各有硬代价:`pg_restore -j` 要求
  `pg_dump -Fc`,**那是压缩格式,会直接毁掉 67 倍的去重**(§2 那个数字)——
  拿 67 倍存储换 10 秒恢复,方向是反的;rclone 已经是 `--transfers 8`。
- **备份**:那 4 分钟的导出是长板,但它凌晨三点无人值守跑,**没有东西在等它**。
  RPO 由"一天一次"决定,把 run 从 6 分钟压到 3 分钟,RPO 一秒不变 —— 却要给线上
  实例的 API 和库加并发压力。有代价,零收益。

**这个结论什么时候失效**(写下来,免得下次靠感觉):DB 到 **~10 GB**(灌库约 4 分钟)
时,"去重换并行"才值得重算;对象到 **~50 GB** 时 rclone 才成为长板;导出逼近备份
窗口时才该并行导出。

**这个数字的诚实边界**,三条:

1. **它是「照着这份 runbook 顺利走一遍」的时间,不是那一天的时间。** 08-29 当天的墙钟是
   数小时 —— 因为**走的过程中撞上并修掉了四个会让流程停死的问题**(余额、拉不到 Docker
   Hub、凭据哪儿都没备、起栈顺序把库先建满)。那几个已经修好了,所以下一次是 10 分钟;
   但**下一次也可能撞上新的**,这正是要定期演练的理由。
2. **DNS 传播不在里面。** 演练用的是全新子域(没有旧缓存),真出事改的是**已经在用的**
   `mica` 记录,而阿里云免费版解析 TTL 下限是 600 秒 —— 最多 10 分钟尾巴,要加上。
3. **不含决策时间。** "确认机器真的救不回来了、决定重建"这一段没有被计时,而它在真实
   事故里往往比恢复本身长。

~~`just restore-drill` 实测过的是「把一份 `pg_dump` 恢复进一次性库并断言可读」这一段,

现在图片能到异地纯属搭内容导出的便车，覆盖范围由 `is_deleted=false` 决定（见 2.1）。
**定下的做法**：rclone 从 RustFS 的 S3 接口 `copy` 到 OSS 的一个前缀，**不经 rustic**。

三个理由：① 图片是**内容寻址、不可变**的，只增不改 —— 镜像即备份，不需要时间点；
② S3 → S3 直传，**不落本地暂存**；③ content-type 等对象元数据随 rclone 一起走，

**用 `copy` 不用 `sync`**：`sync` 会把删除也镜像过去；`copy` 只增不删，对不可变对象正好，
顺带扛住「误删了桶里的对象」。代价是被 `blob_gc` 正常回收的孤儿字节在备份侧会永远留着 —— 体量下无所谓。

**加不加 rclone crypt：倾向不加**，以保住「任何 S3 客户端都能恢复」这个属性；
威胁只剩 AK 泄露，而那种情况下 rustic 那两条腿一样暴露（AK 能删仓库）。

## 6. 双活（active-active）—— 存档结论：不做

不是「暂时不做」，是架构上不该做。四条：

1. **WS 层每文档一个内存 broadcast channel。** 两个节点各持一半连接，同一篇文档的两个
   客户端连到不同节点就**收不到对方的更新**。要修必须上跨节点 pub/sub = Redis，而 Redis
   在 roadmap 里还躺在「可选 / later 基建」没引进来。这不是配置问题，是同步模型的前提被打破。
2. **Postgres 多主本身是重活**（BDR / pgEdge，商业或重型）。而 mica 的写路径是
   `push_update` **全档 decode + encode + upsert**，两个主同时改同一篇的 base 行正好是最坏情况。
3. **新增的运维面**：负载均衡 + 会话粘滞 + 双份证书 + 第二个节点。当前连 Traefik 配置
   都还没纳管（roadmap「生产运维」小节）。
4. **为谁做？** 单管理员自托管产品，没有 SLA 承诺对象。这正是「不要过度设计」要挡的形状。

**双活买的是「零 RTO + 双倍写入吞吐」，这两样现在都不需要，而它要的前提（跨节点 pub/sub）
比它解决的问题更贵。**

### 6.1 可用性的正确下一档：warm standby

真要缩 RTO，走 Postgres 流复制只读副本 +「promote + 切 DNS」的 runbook：

- RTO 从「手工恢复几小时」降到「几分钟」
- **不引 Redis、不改一行应用代码**（应用始终只跟一个主说话）
- 代价：多一台机器的成本与运维面

但**它不替代 5.1**：副本跟着主一起坏（误删、逻辑损坏、勒索都会复制过去），
所以「异地备份」和「热备」是两件事，先有前者。

## 7. 重建：从「机器没了」到「服务回来」

用户 2026-08-28 提出的流程:GitHub Action 手动触发 → OpenTofu 建 ECS → 拿 IP 改 DNS →
复用 ansible 部署 → 从备份灌数据。

**判定:顺序是对的,缺的不是设计,是这条路没有人走过。**

### 7.1 对照现状

| 步骤 | 现状 | 缺口 |
| --- | --- | --- |
| Action 手动触发 | ✅ Deploy workflow 的形状可直接抄 | — |
| OpenTofu 建机器 | ❌ 仓库里没有任何 `.tf` | 整个 provisioning 层不存在(cd-plan §3) |
| 拿 IP、改 DNS | ❌ 无自动化 | 域名天然在仓库外 |
| 复用 ansible | ⚠️ **只有一半** | `ansible/deploy.yml` 只**更新已有栈**。装 Docker、建目录、防火墙、`mica-deploy` 用户 + `command=` 钉死的 key —— playbook 自己写着 CI「never install it」 |
| 从备份灌数据 | ✅ 备份是全的(DB / 内容 / 对象字节每日异地),`restore-drill.sh` 验过 dump 能恢复成**可读**库 | 只验过「恢复进一次性库」,没验过「重建一台机器」 |

**先手工走一遍,再写 Action。** 理由不是保守,是 cd-plan §6 已经写死的那条:*一个没人手工
走通过的流程,不该先写成脚本 —— 没走过就写等于把推演固化成代码,而且脚本一旦存在,人就
不再读文档了,错误会被放大。* 现在 §3 的 RTO 还空着;直接写 Action 意味着**第一次执行它
就是真出事那天**,那时你既不知道要多久,也不知道它哪一步会断。

### 7.2 OpenTofu:用,但不是为了「一次编写、到处运行」

用户想不局限于阿里云(腾讯云 / GCP 也能落),因此倾向 Terraform 这类工具(**具体选
OpenTofu,理由见 7.2.1**)。**结论是用,但要先拆掉一个常见误解,否则会按错误的预期去设计。**

**它不买的**:配置本身的跨云可移植性。`alicloud_instance` / `tencentcloud_instance` /
`google_compute_instance` 是**不同的 resource**,schema 不同,VPC / 安全组 / 镜像 ID /
磁盘类型的语义也不同。「一份 tf 跑遍三家云」是假的 —— 实际形态是
`dr/aliyun/`、`dr/tencent/`、`dr/gcp/` 三份各自的配置。

**它真正买的三样**:

1. **统一的工作流**。三份配置,一个 CLI、一套 plan/apply 心智模型、一样的变量约定。
   不是"写一次",是"学一次"。
2. **`plan` 就是彩排**。这正是 ansible 那半被推翻时的决定性理由(cd-plan §3.2 更新):
   `--check --diff` 当场抓到两个会炸生产的错。建机器这件事同样值得在真花钱之前先看一眼。
3. **`destroy` 让演练变便宜**。演练要反复建了删、删了建,而失败的演练最容易留下**还在计费**
   的 ECS 和弹性 IP。ad-hoc 的 `aliyun ecs CreateInstance` 没有生命周期概念,清理靠人记。

**真正可移植的那一层在机器下面**:一旦拿到「一台装好你公钥的 Ubuntu + 一个 IP」,后面
所有步骤(Docker、compose、Traefik、灌数据)本来就与云无关。**所以边界要划死:OpenTofu
的职责到「一台能 ssh 进去的机器」为止,再往后一步都不许知道自己在哪家云上。** 跨云能力
是靠这条边界保住的,不是靠工具。

**依赖是否该引**:按项目原则「in-house 该留给核心数据面(CRDT / 文档模型 / 同步),不是
平台粘合层」—— 建虚拟机是标准的平台粘合层,用成熟工具是对的。

#### 7.2.1 OpenTofu 而不是 Terraform(2026-08-28 拍板)

**决定性的只有一条:state 加密。** OpenTofu 自 1.7 起支持用你自己的密钥,在写进 backend
**之前**加密 state 与 plan 文件;Terraform 开源版没有这个。这正好打在上一段那个耦合上 ——
state 要放 OSS、和备份同一个桶。tfstate 里本来就有实例 ID 与 IP,而**只要哪天往变量里塞了
口令或密钥,Terraform 会明文写进 state**。有了加密,「state 放对象存储」这件事不再需要
额外小心,少一条要靠人记的纪律。

另外两条是加分项,不是理由,写下来免得被当成理由:

- **许可证**:Terraform 2023-08 从 MPL-2.0 改为 BUSL-1.1(限制竞品用途,非 OSI 认可)。
  自己开自己的机器,BUSL 实际不构成限制 —— 但 Mica 自身刚(2026-08-28)从 AGPL 换成
  MIT/Apache,文档若要写「跑这个来 provision」,MPL 的工具让读者少一个问号。
- **切换成本近乎零**:配置语言兼容。真撞上只有一边有的 provider 或特性,换回去就是改个
  二进制名。**这是个低风险决定,不值得在上面花时间** —— 记下来是为了不再推一遍。

### 7.2.2 分层:造 / 配 / 灌 —— 以及哪一层将来会被扔掉

问过一个好问题:如果以后做 Helm chart 上 k8s,是不是「机器之后的所有步骤」都交给 Ansible?
**不是。分层要按目标是什么切,不是按「统一用一个工具」切。**

| 层 | 目标 | 工具 | k8s 之后 |
| --- | --- | --- | --- |
| **造** | 机器 / 集群存不存在 | **OpenTofu** | ✅ 活着(换 resource,不换工作流) |
| **配** | 机器**内部**:Docker、目录、防火墙、文件 | **Ansible** | ❌ **基本全扔** |
| **灌** | 集群里的工作负载 | **Helm**(可选 Argo/Flux) | ✅ 就是它本身 |

Ansible 的强项是「SSH 进一台机器去改它」。k8s 上**没有要 SSH 进去的机器** —— 用 Ansible
去调 `helm` 只是给 CLI 套层壳,不增加任何安全性(Helm 自己有 `--dry-run`/diff,正是
`--check` 那个被看重的性质)。

**所以要如实记下:今天写的 Ansible provisioning(装 Docker、建 `/data/mica`、compose up)
在迁 k8s 时基本是一次性的。** 这不是不写的理由 —— 容灾是**现在**要的,k8s 是「后面可能」,
仓库里至今一个字都没有,按「不要过度设计」不该为还没拍板的架构牺牲眼前这件事。
但要写**薄**,并且知道它是会被丢掉的那一层。

**真正耐久的资产是恢复逻辑**(`pg_dump` → psql、rclone → 对象存储):它是**数据**不是平台,
VM 和 k8s 上一模一样。所以边界还要再推一条 —— §7.2 说「OpenTofu 的职责到能 ssh 进去为止」,
同理:**恢复脚本不许知道自己跑在 VM 还是 Pod 里**,它只该知道「有个 Postgres 连得上、
有个对象存储写得进」。守住这条,将来那次迁移就只换中间一层。

**state 放哪(容易致命,另见 7.2.1)**:绝不能在那台会挂的机器上。放对象存储(OSS)。同时如实记下
这条耦合:**state 与备份在同一个云账号里**,所以它只扛「机器级」故障,扛不了「账号级」——
这与 §5.3 已拍板的「不做跨账号第二份」是同一个取舍,不是新引入的风险,但要知道它在那儿。

### 7.3 要交给流程的信息(比直觉列的多几样)

| 类别 | 具体 | 缺了会怎样 |
| --- | --- | --- |
| 云凭据 | 建机器用的 AK/SK(建议独立 RAM 用户,最小权限:ECS + DNS) | 建不出机器 |
| DNS | 域名、record ID / RR、解析商 API 凭据 | 机器起来了但没人访问得到 |
| 机器规格 | 付费类型、规格、镜像、VPC、安全组 | —— 用户已列 |
| **备份口令** | **`RUSTIC_PASSWORD`** | **拿到一个完好但永远打不开的仓库**(§2.2)。已由用户单独留存(§5.2),别只存在那台机器上 |
| **备份读取** | OSS 的 AK/SK(可与建机器那对不同) | 读不到备份 |
| **SSH 密钥对** | 公钥必须在**创建机器时**注入(ECS 支持 key pair) | 先有鸡还是先有蛋:ansible 连不上,而你又没法先手工装 key |
| 应用凭据 | `.env` / `.env.secrets` 全套 | **它不在任何备份里**(§2.2),必须从密码管理器带过来 |

**现在就能做的一件零成本预防**:把 DNS 的 TTL 从默认(常见 600s)降到 60s。平时无感,
出事时省下的就是这 9 分钟。

### 7.4 演练 runbook —— 概览（**可执行版在 [`dr-drill.md`](dr-drill.md)**）

> 下面九步是**计划**：它说明要做什么、为什么是这个顺序。真正照着敲的是
> `dr-drill.md`，那份带命令、判据、以及填耗时的空栏。两份都标着 `[推演]`，
> 因为**至今没有人走过**。

> 每步记开始时间。**全程累计耗时就是 RTO 的第一个真实数字** —— §3 那格至今是空的。
> 演练**不要**用生产域名(见 7.5 的证书频率限制),用一个测试子域。

1. `[推演]` **建机器**:`tofu apply`,输出公网 IP。公钥在此步注入。
2. `[推演]` **装底座**:Docker + compose 插件、建 `/data/mica`、防火墙放行 80/443。
   —— 这一层今天完全没有,是 provisioning 的主体。
3. `[推演]` **起反代**:`deploy/traefik/` 那套栈,并建外部网络 `traefik-network`
   (mica 的 compose 以 `external: true` 引用它,不建会直接起不来)。
4. `[推演]` **放凭据**:把 `.env` / `.env.secrets` 从密码管理器写到 `/data/mica/`。
   **注意 `.env.secrets` 是 ansible 从不覆盖的那份**,也正因如此它必须手工带来。
5. `[推演]` **起空栈**:`./dc up -d`(用 `./dc` 不是裸 `docker compose`,理由见
   `upgrade-infra.md` —— 裸的读不到 `.env.secrets`,会用默认口令 initdb 出一颗雷)。
6. `[推演]` **灌数据库**:从 OSS 取 `_pgdump` 最新快照 → `psql`。灌完先跑
   `restore-drill.sh` 的判据(结构 + 行数 + 读路径 join 真能返回内容),再往下走。
7. `[推演]` **灌对象字节**:rclone 从 OSS `mica-blobs` 前缀同步进 rustfs 卷。
8. `[推演]` **切 DNS**:A 记录指向新 IP,等 TTL。
9. `[推演]` **验收**:`/api/health` 报对版本;`/api/ready` 绿;**并且冒烟测真实内容** ——
   登录、打开一篇有图的页面、搜索一个词。版本号证明不了数据回来了。

**每一步都要记下卡住的地方。** 这份 runbook 的价值不在于它写得对,而在于走完之后它会
变得不一样 —— 那些差异就是自动化必须处理的东西。

### 7.5 三个会咬人的

- **账户余额会拦住整件事,而且平时看不见**(2026-08-29 首次 `tofu apply` 实测)。按量付费
  实例要求可用额度 **≥ 100 元**,当时是 81.93 —— 网络层全建好、卡在最后一个资源上,报
  `InvalidAccountStatus.NotEnoughBalance`。关键在于**生产机是包年包月,余额低不影响它跑**:
  这条前提只在你真的要开机器那一刻才被检验,也就是灾难当天。已进 [`dr-drill.md`](dr-drill.md)
  的准备清单;`aliyun bssopenapi QueryAccountBalance` 一条命令能查。
  **这一类前提已经单独成节:见 §9**(还有配额、实名、地域可售性)。

- **Let's Encrypt 有频率限制**:同一组域名每周 5 张重复证书。反复演练会撞上限,届时新机器
  起来了但**没有 TLS**。所以演练用测试子域;真出事那次是第一次签发,不受影响。
- **证书卷不在任何 mica 备份里**(§2.3)。份量轻(可重新签发),但如果撞上上一条,
  "轻"就变成"起不来"。真恢复时若时间紧,可以把旧机器的 `traefik-certificates` 卷一起带走。

## 8. 事故:异地数据库备份静默中断 13 天(2026-08-16 ~ 08-29)

**发现方式值得先说**:不是监控报的,是准备第 7 节那次演练时,顺手看了一眼备份容器的日志。
在那之前,`/api/health` 绿、部署成功、`dr-plan` §0 写着 ✅ —— **所有信号都说备份是好的**。

### 8.1 三个独立的故障,叠在一起

| # | 故障 | 何时引入 | 为什么没被发现 |
| --- | --- | --- | --- |
| 1 | 内容导出**中止整个 run**,连不依赖它的 pg_dump 一起不跑 | 一开始就是这样(`export(...)?`) | 它不是"故障",是设计。直到有东西真的失败才显形 |
| 2 | `deploy/docker-compose.yml` 仍设 `MICA_TOKEN`,而 CLI 已退休该名 | **2026-08-15** 退休 token 时没 grep compose | 报错精准("rename it to MICA_PAT")却打进**没人读的容器日志** |
| 3 | 镜像里 `postgresql-client-16`,服务端已升到 18.6 | **2026-08-28** 我升级 PG 时没动它 | 被 #2 挡在后面,修好 #2 才露出来 |
| 4 | rclone 用的 RustFS 凭据,RustFS **从没听说过** | 不明(至少早于本次) | 被 #2 #3 挡在后面,修完它们才露出来。403 打在**源头**(本地 RustFS),而 api 用另一对名字、一直正常 |

**#4 是「两套名字描述同一个事实」**:只有一个 RustFS,它只接受一对 key。
`S3_ACCESS_KEY_ID`(api 用)和 `RUSTFS_S3_ACCESS_KEY_ID`(rclone 用)是同一个事实的两套名字,
于是它们漂移了 —— 而从外面看什么都正常,因为 api 那半边是对的。

**四个故障是逐层剥出来的**:修好一个才看得见下一个。这本身值得记:**"修好了"不等于
"好了",直到你把整条链真的跑通一次。**

**#1 是放大器**:单独看,#2 只该让「内容导出」这一条腿失败。是 #1 把它变成了三条腿全断 ——
**最不可替代的数据库副本,被最不重要的那条腿挟持了。**

**#3 是我自己造的,而且升级 runbook 没写这一条。** 昨天部署前的备份之所以成功,是因为那条
路径在 postgres 容器**内部**跑 pg_dump(版本自然匹配),恰好把问题遮住了。

### 8.2 时间线

- `2026-08-16 03:01` —— 最后一次成功的自动备份(`_pgdump` 与各工作区谱系同一批)
- `2026-08-15` —— CLI 退休 `MICA_TOKEN`(compose 未跟进)
- `2026-08-28` —— PG 升到 18.6(客户端未跟进);当晚我部署 v0.13.37,备份容器重建
- `2026-08-29` —— 发现。手工补一份 dump 进仓库(**已落地**,633.6 MiB,
  从 postgres 容器内 dump 以绕开 #3);三处修复入库

⚠️ **这条时间线是我第三次才读对的,而前两次都言之凿凿。**

`rustic snapshots` 的输出**按 hostname 分组**(而容器 id 每次部署都变,所以同一条谱系被
切成好几组),我 `tail` 了一下就当成了全部,先后报出「最后一份是 07-31,中断 29 天」和
「08-11,中断 18 天」。正确答案是 **08-16,中断 13 天** —— 要 `grep` 出所有行再排序才看得到。

留着这段不是自责,是因为**错误的版本听起来更严重、也更可信**,而且它当时还派生出一整段
「07-31 到 08-15 之间另有原因、日志已丢查不出来了」的推断 —— 那个空档根本不存在,
是我读错造成的幻觉。08-16 这个日期反而让整件事**连贯**了:08-15 退休 token,08-16 那次
跑的还是旧镜像所以成功,之后某次部署换上新二进制,从此每晚失败。

**教训:对分组/分页的工具输出用 `tail` 取"最新",是在用一个未经验证的前提做判断。**

> **注**:提交 `2ad91dd` 的信息里写的是「29 天 / 07-31」—— 那是更正之前的数字。
> 提交信息不可改,以本节为准。

### 8.3 修了什么

- **腿之间解耦**(`crates/cli/src/backup.rs`):每条腿都跑完,失败记为 `Leg::Failed`,
  run 结束时若有任何失败仍然返回 Err。**这不是退回"部分成功也算成功"** —— 那是这套
  东西当初从 shell 搬进 Rust 要消灭的原罪;变的只是**顺序**:先让每条腿都有机会,再报失败。
- **`MICA_TOKEN` → `MICA_PAT`**(compose)
- **`postgresql-client-16` → `-18`**(Dockerfile.cli)
- **门禁**(`scripts/release-check.sh`):客户端版本 < 服务端版本就拒绝发版。
  Dockerfile 里那条注释**早就写明了这条不变量**,而写明它没起任何作用。
- **rclone 凭据不再是第二套名字**:compose 里默认取 api 那对
  (`${RUSTFS_S3_ACCESS_KEY_ID:-${S3_ACCESS_KEY_ID:-}}`),节点 `.env.secrets` 已就地对齐。
- **objects 腿也解耦**:它是最后一条,`?` 过去只会跳过 retention —— 但形状相同,
  而 2026-08-29 它真的触发了。

**验收(2026-08-29,v0.13.38 上线后真实跑一次 `mica-cli backup run`)**:

```
  database: ran
  content: ran
  objects: ran
```

13 天来第一次三条腿全通。

### 8.4 真正的教训(不是"要加监控")

**同一天里同一形状的 bug 出现了三次**:退休 `MICA_TOKEN` 时没数还有谁在设它;
修 `MICA_API_BASE_URL` 时我只看了 Rust 没 grep compose;升 PG 时没想到还有谁依赖版本号。
`lessons.md` 那条「修了 A,B 是同构的」当时也没人说出口。

**结论**:改一个**名字**或一个**版本**,`grep -rn` 全仓库是修复的一部分,不是可选的谨慎。

第二条:**这份文档里的 ✅ 会腐烂,而且腐烂时没有人被通知。** 所以第 9 节那条复核命令
不是仪式 —— 它是这类失败唯一的出口。**演练的价值也在这里得到了证明:还没开始走,
光是准备就挖出了一起真事故。**

**2026-08-30 补上了那条唯一没被这次演练碰到的根因**:`HEALTHCHECK_URL` 一直是空的 ——
也就是说,08-16 那次静默中断的**直接原因当天并没有被修**,修的是它下游的每一样东西。
现在配上了(healthchecks.io,一天一次 + 2 小时宽限),并实测从生产节点 ping 通(HTTP 200)。
`mica-cli backup daemon` 失败时 ping `<URL>/fail`,所以那次事故会在**第一天**告警,
而不是第 13 天被人在准备演练时偶然发现。

顺带堵掉一个同形状的洞:ping 原来只在**传输层**失败时报警,而 URL 打错一个字符是
404 —— `send()` 会当成成功。**一个永远不会响的开关比没有更糟**,因为它让你相信有人在看。
现在非 2xx 也算失败(v0.13.44 起)。

## 9. 前置条件 —— 平时为真,用时才验

这一节是 2026-08-29 演练逼出来的。当天第一次 `tofu apply` 被账户余额挡下(81.93,
按量付费要 ≥100),而**生产机是包年包月,余额低完全不影响它跑** —— 也就是说这条前提
在灾难当天之前,没有任何迹象说它是假的。

**这一类前提的共同点:它们平时全是真的,只在你真要用的那一刻才第一次被检验。**
监控看不到它们(没有指标在变),日常也踩不到它们(日常不走这条路)。所以只能**主动查**,
而不是等它们证明自己。

| 前置条件 | 一条命令查 | 不满足会怎样 |
| --- | --- | --- |
| **阿里云可用额度 ≥ 100 元** | `aliyun bssopenapi QueryAccountBalance` | 开不出按量付费实例。**实测被它挡过一次** |
| **这三个在 GitHub Secrets**:`MICA_BACKUP_PASSWORD`、`ALICLOUD_ACCESS_KEY`、`ALICLOUD_SECRET_KEY`(后两个在节点上叫 `OSS_*`,同一把 key) | `gh secret list --repo weironz/mica` | **仓库打不开或够不着,前面所有备份等于零**。这是恢复链上仅剩要「被携带」的秘密(§2.2)—— 口令解密、OSS 那对负责"连得上",少任何一个都读不到 |
| **DR 的 SSH 私钥在密码管理器** | 人工确认 | 机器建得出来,进不去。公钥进 CI 变量即可(它本来就公开),**要命的是私钥** —— 只存在某台笔记本上的私钥,在那台笔记本也没了的时候等于没有 |
| **`_config` lineage 真的在产出** | `rustic snapshots --filter-label _config` | 凭据没进备份,重建到"栈起来了、是空的"就停住(v0.13.40 起该 leg 失败会让整个 run 失败,所以这条主要是防"没升上去") |
| **死人开关配着,而且够得着** | `docker exec mica-backup-1 sh -c 'curl -s -o /dev/null -w "%{http_code}" $HEALTHCHECK_URL'` → 期望 **200** | §8 那次静默 13 天,根因就是这条缺着。**只查"配了没"不够**:一个 404 的 URL 看起来配好了,而且永远不会响 |
| **`_pgdump` lineage 是新鲜的** | `rustic snapshots --filter-label _pgdump`(**别 `tail`**,输出按 hostname 分组) | §8 那次:静默中断 13 天 |
| **域名解析的控制权** | `aliyun alidns DescribeDomainRecords --DomainName <域名>` | 机器起来了,没人能访问 |

**什么时候查**:发版的时候。这不是最优节奏,是**唯一真实存在的执行点** —— 与
`roadmap.md` 里「否定式条目只在发版时被看到」是同一个道理。一条需要靠记性执行的检查,
本身就说明它还不是一条检查。

> 演练当天现场发现的这类前提有两条(余额、凭据没备份)。**能被现场发现,恰恰是因为
> 走了一遍**;没走过之前,它们在文档里的形态是「假设成立」。

## 10. 怎么复核这份文档还成立

最容易腐烂的是第 1 节那些数字。一条命令重新取证：

```bash
ssh root@mica.cloudcele.com 'docker logs mica-backup-1 2>&1 | grep -E "pg_dump|snapshotted" | tail -5; docker exec mica-backup-1 rustic snapshots --filter-label _pgdump 2>&1 | tail -3'
```

- 若仍见 `WARN: MICA_BACKUP_PGURL unset` → 5.1 还没做，第 0 节结论原样成立
- 若 `_pgdump` 谱系有快照且新鲜 → 更新第 3 节 DB 那一列，把 RPO 从 ∞ 改成实际节奏

还有一件只能靠真演练回答的：**第 3 节的 RTO 至今是空的。** 要填上它，得在一台干净机器上
从 OSS 拉备份、把服务起到 `/api/ready` 绿，然后记下耗时。这条路没人走过，所以现在
「多久能恢复」这个问题**没有答案**，只有猜测。命令级的工作表是 [`dr-drill.md`](dr-drill.md)，**但全部标着
`[推演]`** —— 一份没走过的 runbook 和没有 runbook 的差别，只是它看起来像有答案。

⚠️ **SSH 别猛敲**：连太密会被云上游限流（一个会话十几次后清一色 `Connection closed`，
等 ~7 分钟自然恢复）。一次 ssh 里用 heredoc 跑完所有检查。
