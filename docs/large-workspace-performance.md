# 大工作区目录性能优化

## 生产取证（2026-10-12，v0.13.49）

用户报告 `database` 工作区打开、切页和日常操作明显卡顿。只读接口确认有 **3,080 个页面、588 个文件夹，共 3,668 条目录记录**，53 个根节点，单个文件夹最多 42 个直接孩子。

同一客户端连接生产服务的抽样：

| 请求 | 响应规模 | 耗时 |
| --- | --- | --- |
| 完整目录，接受 gzip | 解压后 1,755,484 字节；线上 393,084 字节 | 931–979 ms |
| 目录未变化，ETag 条件请求 | 304，空响应体 | 183 ms |
| 对照：security 完整目录 | 53 条记录；线上 5,027 字节 | 285–293 ms |

生产节点内网读取 `database` 完整目录的两次抽样约 70–79 ms，抽测一篇小页面 bootstrap 约 28 ms；另一轮出现一次目录 539 ms，随后重复请求恢复至 70 ms。以上是抽样，不是延迟百分位或保证值。API / PostgreSQL 当时没有 CPU、内存耗尽迹象。未压缩请求另测得 5–6 秒，但浏览器通常会请求 gzip，不能把未压缩结果当作浏览器的实际延迟。

服务端打开页面仅读取该文档，正常正文同步不会发目录变更通知。全树刷新仍有传输成本，尤其首次进入或目录真正变化时；没有证据需要为此次故障更改生产数据库配置或升级机器。

## 根因与修改

目录原来使用 `SliverChildListDelegate`，每次重建都先创建全部已展开行的 widget。每个可编辑行准备拖拽数据和拖拽预览时，两次调用 `_rowsActedOnBy`，而该方法即使只操作单行，也重新扫描所有目录记录建立 ID 索引。

因此成本随 **可见目录行数 × 工作区记录数** 增长。3,668 行全部可见时，每次重建约有 2,690 万次 ID 索引写入。同步状态变化、远端文档更新、鼠标悬停和切页都会触发目录重建；这个成本不限于首次加载。通常折叠场景的可见行较少，不能把全展开的压力测试时间直接套用到日常场景。

修改集中于客户端目录 UI：

- 使用 `SliverChildBuilderDelegate`，只为视口与缓存区域创建行。
- 缓存排序后的树、ID 索引、展开后的行和可见索引，拖拽单行复用 ID 查询。
- 保存输入列表与展开集合的快照；原地增删、同 ID 替换、重命名、移动和重排都使缓存失效。
- 顶层以页面 ID 作为 key，重排时保留行状态。
- 仅目录元数据改变时重新测量自动侧栏宽度，到达宽度上限立即停止，释放 `TextPainter`。
- 修正滚动定位的行高：可编辑行与只读行都包含 8 px 底部间距，完整行高为 46 px，之前可编辑行按 38 px 计算，远处目标会提前停下。

不引入依赖、迁移或存储模型变更。未删除或拆分生产工作区页面。

## 验证边界

新增 10 项回归与 79 项既有相关回归通过，覆盖排序、层级、折叠、孤儿、循环、原地列表/展开集合变化、同 ID 替换、重排状态保留、搜索定位及末行滚动。3,668 行可见的真实 WorkspaceView 测试只挂载 14 个目录行组件；通过实际搜索 UI 定位第 3,000 行，目标行完整落在侧栏视口内。另有 53 根节点、588 文件夹、3,080 页面且只展开活动祖先的合成嵌套场景，验证通常折叠状态下的导航与同步重建。

完整 `flutter test --no-pub`：**1,631 项通过，2 项已有跳过**。`flutter analyze --no-pub --no-fatal-infos` 返回成功，没有 error / warning，136 项现有 info。代码另经独立复核。

Chrome 调试模式的优化前压力测量：物理点击切页 4,854 ms，同步状态触发重建的六次结果为 4,815、4,406、3,186、3,715、3,280、3,885 ms。该场景用 3,668 个合成根行表示全部可见时的工作量，与生产默认折叠状态不同。初建计时因测试 Stopwatch 的静态懒初始化而无效，已丢弃。并行 Flutter 构建会影响 wall time，不能把不同负载/模式的结果直接比较。

停止并行构建和测试后，再用同机 Chrome、1280×900 视口、相同合成场景、同为 **release** 的两个构建顺序测量。基线来自 `efbf4e3`，优化后使用本次修改。计时从导航/同步宿主回调中的 `setState` 开始，到 Flutter post-frame 回调结束；不包括服务端请求。初次加载的无效 Stopwatch 样本仍丢弃。

| 操作 | 优化前 | 优化后 |
| --- | --- | --- |
| 物理点击切页后的重建 | 2,776.3 ms | 52.1 ms |
| 同步状态重建（6 次中位数） | 2,359.7 ms | 48.6 ms |
| 鼠标滚动至末行 | 可达 | 可达 |
| 浏览器页面异常 | 0 | 0 |

这些结果证明已消除本次复现的目录二次开销，不能解读为整个生产操作端到端的加速比例。完整原始操作计时见 [对照数据](assets/large-workspace-benchmark.json)，[优化后浏览器截图](assets/large-workspace-optimized.png) 使用合成页面名称。调试实例一次热重启因调试连接超时失败；重新启动并使用 release 构建完成了上述实际 UI 验证，未将调试连接故障计为页面异常。

生产取证只读目录元数据及用于测量的一篇现有文档；原始目录样本保存在本机临时目录，没有提交仓库。性能与 UI 回归使用合成数据，不修改生产页面。浏览器实测使用真实 `WorkspaceView`、目录行和导航交互，宿主以合成 bootstrap 代替服务端网络。

本次优化已随 v0.13.50 部署到生产 Web；桌面端需要更新至同版客户端。生产接口的下载、WS 网络与页面本身的大内容渲染不在这个合成目录压力测试的覆盖范围内。
