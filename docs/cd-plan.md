# CD 与 provisioning —— 现状、症状、拆分方案

> 2026-08-02。起因是一句直觉：「我们的 CD 流程怪怪的，一点不够简洁优雅」。
> 本文把那句直觉拆成可验证的症状，并给出拆分方案 —— **但不含实施**，因为最关键的
> 一步（手工走一遍 provisioning）还没有人做过。
>
> 相邻文档：`release.md` 是**当前**的发版步骤（权威），`deploy.md` 是升级**已有**栈，
> `dr-plan.md` 是容灾策略。本文管的是**这套东西应该长成什么样**。

## 0. 两句话结论

1. **一个 `vX.Y.Z` tag 同时驱动三条节奏完全不同的发布线**，于是最慢最重的那条
   （Windows 安装包）决定了最快那条（服务端配置改动）的节奏。
2. **provisioning 层根本不存在。**「给台新机器就能起全套」这个目标今天做不到 ——
   缺的不是 CD 的最后一公里，是从零造出一个环境的那一整层。

## 1. 症状：三条发布线焊在一个车头上

| 产物 | 面向谁 | 想要的节奏 |
| --- | --- | --- |
| api + web 镜像 | **自己的一个节点** | 快、频繁、常常只是改配置 |
| Windows 安装包 | **真实用户** | 慢、有意义、要签名、会弹更新提示 |
| mica-cli 三平台二进制 | 用户的 MCP 配置 | 中等 |

后果不是理论上的。**0.13.6 本质上是为了送一行 compose 配置**，代价是一次完整的
Flutter Windows 构建 + 安装器冒烟，并且**给所有桌面用户推了一个什么都没变的更新**。

### 1.1 实测到的症状（2026-07-30 ~ 08-02）

- **Deploy workflow 连续两次被节点拒绝。** 只要 `deploy/docker-compose.yml` 变过，
  节点的 sha256 指纹校验就拒绝执行，必须回到笔记本上跑 `just deploy-prod`。
  **当兜底路径成了主路径，就是主路径没设计好。** 而配置类改动占了很大比例 ——
  那几天里配额、注册开关、备份变量，三次全是。
- **0.13.7 整版作废。** `images (cli)` job 挂了（我写的 rclone 阶段两个 bug），而
  api/web 镜像和安装包**已经发布**。tag 不可变，只能重发 0.13.8。**一个产物失败让
  整版报废**，是「所有产物绑在一个 tag 上」的直接代价。
- **所谓 CD 其实是「开发者笔记本部署」。** `just deploy-prod` 同时需要能连 GitHub
  和能 SSH 节点 —— 那台机器只有你的笔记本。

## 2. 拆分方案：把「发版」和「部署」分开

它们现在被焊成了一件事：**每次部署都必须先发一次版**。

- **服务端**：main 每次推送就构建镜像，用 **git SHA** 打标签。部署 =「把 prod 指到
  SHA `abc123`」。compose 与镜像天然同源，**指纹校验变成恒真，那个失败从结构上消失**。
- **用户面**（桌面安装包 / CLI）：继续用 `vX.Y.Z`，保持慢节奏、签名、更新提示。
- 顺带把版本号从三处（`pubspec.yaml` / `kAppVersion` / 根 `Cargo.toml`）收敛成单一
  来源 —— 那是独立的小赢，但只有拆开之后才显得干净。

拆开之后：**改一行 compose = 推 main + 一条部署命令**，不 bump 版本、不构建 Windows、
不打扰用户。

## 3. 缺的那一层：provisioning

「一键拉起新环境」缺的不是 CD 的最后一公里，是**从零造出环境的那一整层**：

| 缺口 | 现状 |
| --- | --- |
| 装 Docker / 建目录 / 防火墙 | 完全没有 |
| **Traefik** | 2026-07-31 才纳管进 `deploy/traefik/`（此前只活在节点上）。**新机器没有它 = 没有 TLS、没有路由** |
| `mica-deploy` 用户 + `command=` 钉死的 key | 手工装。deploy.yml 自己写着 CI「never install it」—— 那么谁装？今天的答案是「你，手工」 |
| 密钥两分 | **必须新生成**（`JWT_SECRET`、PG 口令、S3 keys）vs **必须带过来**（`RUSTIC_PASSWORD`、OSS AK，否则新机读不到备份）。今天没有任何机制区分这两类 |
| DNS | 天然在仓库外 |

### 3.1 分层

```
provision（造）  →  deploy（更新）  →  restore（灌数据）
```

- **provision**：裸机 → 能服务的空实例。手动版已写成 runbook（在 Mica：
  「从零拉起一个 Mica 服务端（手动，命令级）」），**但整条路径至今没人端到端走过**。
- **deploy**：把已有栈滚到某个版本。今天有，就是第 2 节要重构的那半。
- **restore**：把数据灌回去。见 `dr-plan.md` §5 —— 恢复路径存在了，同样没人走过。

**收敛点**：provision + restore 做成了，**裸机恢复 runbook 顺带就有了**，而
`dr-plan.md` 里那格空着的 RTO 也才第一次有真实数字。

### 3.2 手段

倾向**一个幂等脚本**，不引 Ansible（单机 docker + 单管理员，Ansible 是新依赖加新
心智模型）。写成 bash 还是 `mica-cli provision` 待定 —— 后者有先例：备份编排刚从两个
shell 脚本收进 `mica-cli backup`，而 mica-cli 每次发版都出 linux-x64 二进制，新机器
一条 `curl` 就有。

那四个「新生成」的密钥在脚本里就是四行 `openssl rand -hex 32`，写进 `.env`，
**你从头到尾不经手**。今天的状态是「填错了会当场拒绝启动」（0.13.8 起），
那时才是「根本轮不到你填」。

**边界**：root 密码那一步**不自动化**。正确做法是你自己 `ssh-copy-id` 装公钥、再禁用
密码登录，之后全程 key 认证 —— 一个需要密码才能重跑的脚本不是幂等的。

## 4. 重构时必须留住的三样

现在这套里有三样是真做对了，换发布线时不能一起扔：

1. **`command=/usr/local/sbin/mica-deploy` 钉死的 SSH key** —— CI 只能执行
   `deploy <version> <sha>`。deploy.yml 里那句「CI may READ the fence that limits
   it, never install it」是清醒的。
2. **部署后验**摸库的 **`/api/ready`** 并断言版本 —— 不是不摸库的 `/api/health`。
3. **安装包的安装-启动冒烟** —— 发布前拦，且已根治过一次 mutex 竞态。

## 5. 刻意不做的

- **双活**：见 `dr-plan.md` §6。WS 层每文档一个内存 broadcast channel，双活必须先上
  跨节点 pub/sub（Redis）；PG 多主是重活；单管理员产品没有 SLA 承诺对象。
- **把三份 compose 合成一份带 profile 的**：那份文件是运维半夜要读的东西，可读性比
  「少一个文件」值钱。三份各有明确职责（dev / quickstart / Traefik 生产）。

## 6. 下一步的顺序（不要跳）

1. **找台测试机，照 Mica 那份 runbook 手工走一遍。** 把 `[推演]` 逐条变成
   `[已验证]`，填上耗时（那个数字就是 RTO 的下限），并回答那两个问号：RustFS bucket
   要不要预建、整条路径要多久。
2. **然后**才写 provisioning 脚本。runbook 自己开头就写着：*一个没人手工走通过的
   流程，不该先写成脚本* —— 没走过就写等于把推演固化成代码，而且脚本一旦存在，人就
   不再读文档了，错误会被放大。
3. **再**动发布线拆分（第 2 节）。它独立于 1 和 2，但风险更高：`deploy-prod` 从 tag
   取 compose 与策略脚本，改动路径会让**已发布版本部署不了** —— 2026-07-31 脚本改名
   时已经踩过一次，靠加新旧路径回退才没炸。

## 7. 怎么复核这份文档

最容易腐烂的是第 1 节那些症状。判据很简单：

- 改一行 compose 之后，Deploy workflow 还会不会被节点拒绝？（今天：**会**）
- 部署一次服务端配置改动，要不要 bump 版本号并构建 Windows 安装包？（今天：**要**）
- 给一台新机器 + root 密码，有没有一条命令能把整套起来？（今天：**没有**）

三个问题都变成「不会 / 不要 / 有」的那天，本文可以删掉。
