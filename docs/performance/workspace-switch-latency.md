# 工作区切换延迟：评估与方案（2026-08-25）

用户报「切换 workspace 延迟很大」，目标「瞬间无感」。这份文档记录重估的结论、同类
产品的做法、候选方案与取舍。**先看第 3 节** —— 有几条我们一直当成前提的东西并不成立。

## 1. 延迟由什么构成

对生产节点实测（本机直打接口，不是从客户端里量的，见第 6 节）：

| 请求 | 耗时 | 响应体 |
| --- | --- | --- |
| `members` | 50–100ms | 215 B |
| `views`（5 页工作区） | 50ms | 2.2 KB |
| `views`（3077 页工作区） | 145ms | **1.75 MB** |
| `bootstrap`（单页，冷连接） | 118ms | 16 KB |
| `bootstrap`（同一请求，热连接） | **49ms** | 16 KB |

最后两行是关键：同一个请求差了 ~70ms，**那是 TLS 握手**。

### 桌面端没有连接复用

`clients/mica_flutter/lib/api/client.dart` 里 14 处全部是顶层 `http.get/post/…`。
package:http 的顶层函数每次新建 Client、用完就关：

```dart
// http-1.1.0/lib/http.dart:163
Future<T> _withClient<T>(Future<T> Function(Client) fn) async {
  var client = Client();
  try { return await fn(client); } finally { client.close(); }
}
```

全仓唯一的 `http.Client()` 实例在 `updater_desktop.dart:83`。所以**每个 API 请求都
付一次完整握手**，切换时并发发出的两个请求各付一次。

- 已实测的 145–190ms 里，**约 70–110ms 是握手**，服务端干活 + 传输只有 35–70ms。
- **这一项 web 端不存在**：浏览器有连接池，服务端已提供 h2。桌面与 web 的延迟构成
  是两回事，不要混着谈。

### 冷路径：不是慢，是错

`_viewsByWorkspace` 初值 `const {}`（`main.dart:346`），在线写入点只有
`main.dart:5512`，一次只写一个工作区；启动只加载被恢复的那一个（`:1067`）。因此
**一个会话内首次切到任何工作区必然缓存未命中**：

- `_rememberedViewOf` 返回 null → 投机 bootstrap 发不出去 → 退化成两趟串行。
- 侧边栏拿到 `const []` → 渲染 `sidebarNoPagesTitle`「还没有页面」
  （`main.dart:8744`）。**树没加载完却说这个工作区是空的。**

### 正文每次都闪首页

`main.dart:1901` 无条件 `_selectedBootstrap = null`，编辑器随即回落到 Home 面板
（`:9452`），**即使页树是缓存命中**。观感是「侧边栏已经选中了这一页，主区却显示首页」。

### 两处偶发的整趟

- `_ensureFreshSession()`（`main.dart:1137`）是 `_run` 的第 0 个 await，排在
  「同帧上树」的 setState **之前**。平时是 microtask，token 进入 5 分钟临期窗口时是
  一整趟 `/auth/refresh` —— 那时连侧边栏高亮都要等它。
- 切换入口无并发门禁（`:6154`/`:6235`），连点两个工作区会有两条
  `_loadSelectedWorkspaceViews` 竞争写同一份 `_selectedBootstrap`/`_selectedView`。

### 修正后的账（桌面）

| 场景 | 现值 |
| --- | --- |
| 热（本会话切过该工作区） | 145–190ms，正文闪 Home |
| 冷（本会话首次切入） | 250–350ms，前半段侧边栏显示「还没有页面」 |
| token 临期窗口 | 再加 90–150ms，且卡在第一帧之前 |

**1.75MB JSON 的解析排在最后一位**（本机 3664 条 16–45ms，AOT 基准更低）。不要先动它。

## 2. 同类产品怎么做

### AppFlowy（Flutter 同构，首要参照系）

- Rust 侧本地优先：`open_workspace` 本地 sqlite 命中就直接用，`tokio::spawn` 后台
  校正；查不到才 await 网络。页树、正文同一模式。
- **UI 层刻意没有乐观切换**：先 emit `isLoading`，await FFI 成功才换
  `currentWorkspace`，失败保持旧值。给的是全屏 `barrierDismissible: false` 菊花。
- 刻意没用：骨架屏（全仓搜不到）、预取、per-workspace 记住上次打开的页
  （`lastOpenedSpaceId` 是全局单键）。
- 接受的破绽：`on_workspace_opened` 失败被吞（会报「打开成功」但侧边栏空）。

### AFFiNE（web/Yjs，第二参照系）

- 页树纯本地 Yjs observe，零网络参与首屏。远端 peer 把 diff 写进 **local storage**，
  前端订阅 local storage 再 applyUpdate —— **单向漏斗，远端永不直接碰内存 doc**。
- 渲染门槛是 `ready`（yjs doc 里有数据）而不是 `synced`。
- **反面教训**：`ready` 要求本地数据非空。它们曾把「内容看起来非空」当成「已加载」，
  在没加载完的 doc 上写，**真丢过数据**（PR #5798 / #6110 / #6111 三个 hot-fix），
  最终引入显式 `rootDocLoaded`，并配了一个**以切 workspace 为场景**的 e2e：注入远端
  stuck，断言必须一直骨架屏、不能显示空列表。
- 旧 workspace 销毁不在关键路径：release 只减引用计数，真 dispose 交给 1s 的 GC
  定时器。副作用是**来回切在 1 秒内是零成本命中**。
- 别抄的洞：`canGracefulStop` 恒 true 挂着 TODO，`disconnectDoc` 会丢弃排队的 save。

### Notion（唯一有公开提速数字，且不是本地优先）

- 本地是 **best-effort 的 LRU 记录缓存**，官方原文：不保证哪些记录在本地、能留多久。
- 打开页面是**本地优先 + 全有或全无**：本地缺任何一块就整页转服务端，绝不渲染半棵树。
- 导航提速机制是**赛跑**：本地读与 API 请求同时发，谁先返回用谁 —— 因为实测低端
  Android 读盘比走 API 还慢。
- 公开数字是导航快 20%（2024）/ 50%（2021）。**它从未宣称「瞬间」。**

## 3. 那个「共同前提」是假的

原本猜：它们快是因为「页树和内容本来就在本地」。**反例比正例强**：

- 样本里最彻底本地优先的两家恰恰**切换最慢**。Obsidian 首开 vault 要跑全量索引
  （98k 文件移动端曾 314,929ms），并且回避了原地切换 —— 切 vault 是开新窗口。
  Logseq 切图是双向成本：先把旧图 DataScript 落盘再恢复新图。
- 唯一有公开提速数字的 Notion **不保证**本地有页树。

**真正的共同前提：切换路径上不等一次全量获取 / 全量重建。** 手段各异，但没有一家让
「取页树这一趟」出现在渲染关键路径上。

所以该质疑的**不是「要不要向服务端要页树」** —— 照要，P1c 纪律（服务端 4xx/5xx 必须
冒出来，不能被陈旧缓存掩盖）也要保留。该质疑的是另外三条隐含前提：

1. 切换必须先把正文清空再等它回来（`main.dart:1901`）—— 三家都不这么做。
2. 本地镜像只配当失败兜底（`:1906` 的 `_offlineNav` 门禁）—— **「先渲染后校正」和
   「用缓存冒充服务端成功」是两回事**，前者不违反 P1c。
3. 本地读一定比网络快 —— Notion 有实测反例，这条要埋点验证而不是假设。

### 三家都刻意没用的

- **没有一家在切换入口预取全部 N 个工作区。**
- **没有一家用乐观 UI 替代数据可用性。** AppFlowy 在与我们完全相同的约束下刻意没做。
- **没有一家渲染半棵树。** Notion 全有或全无；AFFiNE 宁可一直骨架也不显示空列表。
- **骨架屏本身没有公认优势。** 唯一可引的对照实验（Viget, n=136）里骨架屏三项指标
  全垫底。有依据的那条是反过来的：**不要把已经显示出来的内容换成 loading**。

## 4. 方案

### A1. 进程级共享 http.Client（桌面）——【先做】

`client.dart` 的顶层 `http.*` 全部改走一个长寿命 `http.Client` 单例。dart:io 的连接
复用是白送的（`persistentConnection` 默认 true、`idleTimeout` 15s）。

- 收益：第二次起每请求省 70–110ms，热路径 145–190ms → **约 70–115ms**。
- 边界：HTTP/1.1 下两个并发请求本来就要两条连接，**救不了第一次切换**，只救 15s 内
  的后续切换。要让第一次也快，可在打开工作区菜单时发一个极小请求把连接烫热 ——
  **预取连接，不是预取数据**，这是本项目里最划算的「预取」落点。
- 别追 h2：dart:io 全无 HTTP/2，换 package:http2 等于重写网络层，违反依赖纪律。
- 风险：接近零。工作量：半天。

### A2. 正文交给 CloudSyncSession 铺底，HTTP bootstrap 不再写正文

这是剩下最大的一块观感收益，也是**唯一有丢字风险**的一块，做法必须写死。

- `main.dart:1901` 不再把正文清空等 HTTP；让 `_reconcileSync()` 先起
  `CloudSyncSession`。该会话 `connect()` 已经是「先本地后网络」：`_seedFromLocalOnce()`
  从磁盘 yrs 副本渲染（零网络），再开 socket；因为 `_doc != null`，发的是 `sync.pull`
  而非 `sync.bootstrap`，服务端数据一律 **CRDT merge**。
- HTTP bootstrap 的返回值只取元数据，**正文的唯一写入者收敛到 `_applyCloudBlocks`**。

**为什么不能用最直觉的写法**（先塞缓存 bootstrap，网络回来再整体替换）——会**真丢字
且不可逆**：HTTP bootstrap 是从 yrs base 物化出来的 JSON，不带 CRDT 元数据，结构上
只能整体替换 → 编辑器 reconcile 按服务端列表重建节点（本地新增块直接丢弃）→ 用户
接着打字 → `set_block_text` 对 CRDT 做最小 diff → 把新内容 delete 掉推给服务端 →
而 `room.broadcast` **排除发送者**，不会有回显救回来。

- 收益：正文不再闪 Home，切回待过的工作区接近零等待。
- 风险：中，但机制上可控（全程 CRDT merge）。工作量：2–3 天。

### A3. 页树镜像预热 + 修 clean-replace

- 启动/空闲时从磁盘镜像预热 `_viewsByWorkspace`，让首次切换也走缓存命中路径。
- 修 `_cacheCloudPageTree`（`main.dart:5540`）+ `local_offline_io.dart:276` 的
  **origin 级 clean-replace**：现在写镜像只写内存 map 里有的工作区，**会抹掉本次会话
  没访问过的工作区的页树** —— 所以镜像今天的覆盖面和内存缓存一样窄。要改成按
  workspace 粒度合并。
- `main.dart:8744` 的「还没有页面」：在「树未加载」与「树确实为空」之间加区分。
- **必须显式设计**：页树是 REST + 后写胜，**没有 CRDT 兜底**。先画镜像再被
  `main.dart:5511` 整体替换，会打掉用户在这 100–200ms 窗口里的重命名/新建/拖动。
  需要一个待定本地变更集，覆盖时丢弃 revalidate 结果或重放变更。
- 风险：中。工作量：2–3 天。

### A4–A6（小改，各半天以内）

- `_ensureFreshSession` 移出关键路径（后台续期，或与 action 并发）。
- 切换入口加并发门禁或请求代际号。
- 祖先展开改用 `_selectedView` 驱动而非 `bootstrap != null`（`:7975`）。

### 方案 C（暂不做）：登录时一次性取回全部工作区页树

借 Notion `loadUserContent` 的形状。切换退化成纯内存操作，语义比 A3 干净。
**先不做的理由**：典型用户有几个工作区、树多大，我们没有数据；3077 页已经 1.75MB，
5 个就是 8.75MB 启动传输。而且它**不解决正文**。前置条件是给 `listViews` 加
ETag/If-None-Match —— `crates/` 下 grep `etag|if-none-match|cache-control` 命中 0 —— **已于 v0.13.27 补上**（见下），
现在每次都是全量传输 + 全量查询，任何预取/revalidate 的成本都被这一点放大。

## 5. 推荐

**分阶段做 A，第一阶段只做 A1 + A4/A5/A6 + 埋点。**

这几项零风险、约一天半，且 A1 的收益（70–110ms/次）**大于其余全部候选的总和**，还是
唯一一项不需要在「新鲜度 vs 瞬时」之间取舍的。埋点是后续判断的前提。

阶段二做 **A2** —— 机制已经存在（`_seedFromLocalOnce` + `_applyCloudBlocks` 都是现成
件），不需要新写核心逻辑，只需把正文写入者收敛到一处。

阶段三才考虑 **A3**，它的复杂度全在「页树没有 CRDT 兜底」这一条上，收益只覆盖
「本会话首次切入」。

### 明确不做

- **不做乐观 UI / 假动作。** AppFlowy 在同样约束下证明了不需要。
- **不做「打开菜单时预取全部工作区的树」。** 没有 ETag，N 个工作区 = N × 全量。
- **不碰 P1c 纪律。** 要在代码注释里立下这条区分：**「先渲染后校正」≠「失败兜底」**，
  否则下一个人会当成绕过纪律删掉。
- **不动 isolate / compute。** 排最后，且 Flutter Web 上 `compute()` 根本不开线程。
- **不追 HTTP/2（桌面）。** 天花板就是长寿命 client + 连接保温。
- **不做骨架屏动画设计。** 有依据的是「不要把已显示的内容换成 loading」。

### 目标口径要改

「瞬间无感」比 Notion 自己公开声称的还高，而且不可证伪。改成：

- 点击 → 首帧出现新工作区的选中态与页树：**< 100ms**，且中间态**不出现假空态**。
- 服务端校正到达：**P95 < 300ms**，且不产生视觉跳变、不打断 IME 组字。
- 全程无内容丢失（回归测试钉死）。

### 必须配的回归测试

1. **抄 AFFiNE 那个 e2e 的形态**：注入永不返回的 listViews/bootstrap，切到本地无镜像
   的工作区，断言看到骨架而**不是**「还没有页面」。
2. **丢字红线**：离线编辑未推送 → 切走 → 切回 → 断言字还在，且服务端不曾收到删除。
3. **切换耗时打点**，否则「快了」无法证伪。

## 6. 实测结果（2026-08-25，三阶段落地后）

本地 dev 栈 + demo 账号，**debug 构建**，桌面端。`MICA_TRACE_SWITCH=true`。

| 路径 | total | shell | mirror | tree | body |
| --- | --- | --- | --- | --- | --- |
| 冷（本会话首次） | 109ms | 0 | – | 88 | 11 |
| 热 | 67ms | 0 | 2 | 57 | **2** |
| 热 | 135ms | 0 | 1 | 125 | **2** |
| 热 | 273ms | 0 | 132 | 128 | **2** |

- **`shell` 恒为 0–1ms** —— 「侧边栏与选中态同帧完成」此前只是代码推导，现在有数。
- **`body` 稳定 2ms** —— A2 生效，正文由镜像瞬间铺底，不再闪首页。
- 冷路径上 members 与 views 并发（各 ~86ms 且重叠），A4 生效。
- 剩下的几乎全是 `tree`（views 请求本身）。

**埋点当场抓到一个自制回归**：`_seedBodyFromMirror` 一开始被写成 `await`，串在页树
请求前面。"只是本地读一下"在大文档上实测 **836ms**，热路径因此 1054–1563ms，比冷
路径慢十倍。改成并发后才有上表的数字。教训见 `lessons.md`。

**其余三项手工验证**（都在本地 dev 栈上做，不碰生产）：

- **丢字红线**：页面打标记 → 立刻切走 → 切回，文字还在，且服务端 `content_text`
  确认收到、不曾收到删除。宽松版与「打完不留间隔立刻切走」的严格版都过。
- **侧边栏拖拽**：拖到底边会滚，指针挪回中部后停住 —— 相隔 3 秒两张截图逐像素一致，
  落点指示线就在中间。
- **骨架行**：`docker pause` 掉 API（照 AFFiNE 那条 e2e 的形态）再切到无镜像的工作区，
  侧边栏画占位行，不再显示「还没有页面」。

## 7. 诚实标注（已按实测修订）

**仍未验证**

1. **A1（共用 http.Client）的收益没有量到。** 它省的是 TLS 握手，而实测是在
   localhost 上做的，握手成本近似为零。这条仍是推断——虽然「同一 bootstrap 冷
   118ms / 热 49ms」那组对照支持它。要证实必须对着远端 HTTPS 量。
2. **所有数字是 debug 构建 + localhost。** dev 服务器单个请求就要 ~86ms，绝对值不能
   搬到生产。release/profile 下重测才有产品意义。
3. **A5（切换并发门禁）没有专门验证。** 连点两个工作区的竞态没构造出来。
4. **A4 的临期续期分支没有验证。** 需要一个正好进入 5 分钟窗口的 token。
5. **两条自动化回归测试仍然缺席**（第 5 节列的第 1、2 条）：假空态的 e2e、丢字红线的
   端到端测试。目前只有手工验证 + 纯函数单测（`restSnapshotMayReplaceBody`）。
   手工验证不会在 CI 里重跑，也就挡不住下一次回归。
6. **典型用户有几个工作区、树多大 —— 仍无数据。** 方案 C 与预热成本的判断依赖它。
7. **文档正文镜像的命中率仍是推测。** A2 的收益取决于「切回上次待过的工作区」是否高频。

**已经不再是问题的**（原第 6 节里已被实测取代的条目）

- 「145–190ms 的构成从未分解过」→ 已分解，见上表。
- 「decode 是否 JIT 数字」→ 不再要紧：decode 从未出现在关键路径的耗时里。
- 「同帧上树从未实测」→ 已实测，`shell` 0–1ms。
- 「`_selectedView.objectId` 是否就是 `_reconcileSync` 要的 documentId」→ 是。
  服务端按路径里的 `document_id` 查，客户端传的正是 `view.objectId`，镜像造出的
  bootstrap 因此自带正确 id，`_reconcileSync` 一行没改。

## 9. v0.13.27：ETag 落地（2026-08-25）

第 4 节列的「前置条件」已经做了：`GET .../views` 现在返回 `ETag` 并支持
`If-None-Match`。

**ETag 由行本身算出，不是 `max(updated_at)`** —— `views.updated_at` 没有触发器，
全靠每条 UPDATE 手写维护，漏一条客户端就永远卡在过期的树上。过期比慢糟得多，
内容哈希不可能过期。哈希覆盖全部序列化字段（ETag 是对响应体的承诺，不是对某个
调用方用途的承诺）与查询形状。

本地 3700 页实测：

| | 状态 | 字节 | 耗时 |
| --- | --- | --- | --- |
| 带 If-None-Match | 304 | 0 | 63–79ms |
| 不带（对照） | 200 | 1.6 MB | 141–172ms |
| 改一页名字后 | 200 | 1,612,083 B | 陈旧被正确检出 |

客户端只在**真的持有树**时才发条件请求（否则 304 会让侧边栏空着），ETag 存在
`viewsEtag:<ws>`，与镜像一起跨重启；埋点把命中标成 `tree(304)`，真机已确认。

### 工作区大小的实测（curl，本地，热连接）

| 页数 | views 字节 | 服务端+网络 |
| --- | --- | --- |
| 23 | 9.8 KB | 13ms |
| 100 | 43 KB | 16ms |
| 1000 | 435 KB | 78ms |
| 3700 | 1.6 MB | 250ms |

约 13ms 底噪 + 0.064ms/页；其中数据库只占 26ms，其余是序列化与传输。生产真实分布：
每工作区页数 p50=355 / p90=803 / max=3664。

**正文轴几乎不是问题**：bootstrap 在 p50（~1.6KB）6ms、p99（31KB）8ms，只有极少数
巨型文档（库里有个 3.67 MB 的）才有成本。

### 两条已被推翻的判断

- **「服务端没有压缩」是错的。** 那是拿本地 dev API 量的就推到生产。生产实测：
  不压缩 1,754,317 B / 352ms，gzip 392,917 B / 208ms，`Server: nginx/1.31.4` ——
  前面的 nginx 一直在压。一度加上的 `CompressionLayer` 因此是重复劳动（还把 CPU
  从 nginx 挪进应用），已撤回。
- **字段裁剪不划算。** 12 个字段客户端只用 7 个，原始省 48%，但**压缩后只省 16%**
  （UUID/时间戳本来就好压），还要动 API 契约（MCP、CLI 都是消费者）。
