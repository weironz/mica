# 2026-10-16 生产全局搜索偶发延迟定位

用户现象：Windows 桌面全局搜索偶尔很慢，随后又恢复正常。本次只诊断 Mica，
没有修改网络、生产配置或应用代码，没有清空页缓存、Swap、重启服务或人为制造冷启动。
版本为 v0.13.52。下面请求少量、顺序执行，响应正文没有输出到日志；PAT 只在内存用于原有认证。

## 公网与服务器内部实测

Windows 本机通过公网 HTTPS 请求 `/api/search`，每次是新 curl 进程，
故连接成本不等同于桌面共享客户端的复用连接。全局搜索均 include_folders=true，未指定 prefer_workspace。
使用已有账户权限，单次最多返回 50 条；结果正文未保存，只保存时间、HTTP 状态和字节数。

| 查询 | 公网总时间 | TCP/TLS 完成时刻 | 首字节时刻 | 响应大小 |
| --- | ---: | ---: | ---: | ---: |
| 不存在的测试词，首个搜索 | 15.876 s | 0.068 s | 15.876 s | 14 bytes |
| 数据库 | 0.577 s | 0.130 s | 0.553 s | 23,371 bytes |
| postgresql | 0.912 s | 0.114 s | 0.890 s | 28,643 bytes |
| a | 0.576 s | 0.120 s | 0.564 s | 13,692 bytes |

首个健康请求 1.431 s，其中 TCP/TLS 1.375 s，说明连接本身也有波动；
最后一次健康请求恢复到 0.106 s。不能把所有网络请求一概视为零成本。
但 15.876 s 的慢搜索只有 14 bytes，且连接在 68 ms 已完成，主要等待位于建连后、首字节前。
单凭 TTFB 仍不能完全区分应用处理与建连后的传输停顿，必须结合内部测量判断。

随后在 Mica 主机直接访问 API 容器 HTTP，避开公网、TLS 和入口代理，
使用已有备份服务中的 Mica PAT，未复制/新建凭据。相同查询响应大小与公网一致：

| 查询 | 内部总时间 | 返回条数 |
| --- | ---: | ---: |
| 不存在的测试词 | 0.255 s | 0 |
| 数据库 | 0.361 s | 50 |
| postgresql | 0.462 s | 50 |
| a | 0.361 s | 50 |

内部健康请求为 1.4–9.2 ms。两轮先后执行，后者已经受前一轮预热影响，
不是同一时间的严格网络减法对照，也不能由此声称内部已经重现 15 秒。

## 缺页 / 缓存证据

API 空闲 45 秒后，直接 HTTP 依次执行三次相同的无结果查询，记录对应 cgroup 差分：

| 次序 | 总时间 | API 计费物理读 | 文件页 refault 增量 | major fault 增量 |
| --- | ---: | ---: | ---: | ---: |
| 空闲后首查 | 0.193 s | 14,761,984 bytes | 3,604 | 5 |
| 紧接第二查 | 0.078 s | 0 | 0 | 0 |
| 紧接第三查 | 0.140 s | 0 | 0 | 0 |

这段中的匿名页 refault 增量均为零，API 存量 Swap 约 162.82 MiB 未变；
所以这次测到的是文件/代码页重新读入，不能把约 14 MiB 全称为 Swap 换入。
cgroup 差分还可能包含并发业务和后台处理，不能把每一页都绑定到一个具体函数。
现象支持工作集被回收后重新读入带来的波动，但没有捕获到 15 秒那次的内部阶段，
因此完整尖峰根因尚未证实。

`document_yrs_base` 约 15,134 行、正文 76,290,579 bytes（约 72.8 MiB），
没有未来 updated_at 或最近一分钟变化的行。全局 BodyIndex 常驻保存折叠正文，
每次查询仍扫描该索引。源码中的启动预热不是持续驻留保证。
实际启动日志也确认已成功预热 15,132 篇，没有预热失败记录；因此不能把此次慢首查
简单解释为“服务刚启动、索引尚未建立”。
只读 EXPLAIN 的增量刷新探针实际执行 11.127 ms，过滤 15,134 行、零返回，
1,562 shared buffer hits、零 shared reads；这只能证明该次刷新 SQL 正常，不能回推历史尖峰。

## 桌面链路的确定等待

- `dialogs.dart:269` 每次输入等待 280 ms 后发请求。
- `searchScopeFor` 正常只发一次全局 GET，只有抛错时再串行回退当前工作区；不存在逐工作区循环。
- Windows REST 使用 Dart package:http 的 IOClient，共享客户端复用连接。
- 已发请求不会随继续输入取消；旧响应按当前 query 丢弃，多次停顿可能产生重叠搜索。
- 结果必须等待完整 body、JSON decode 后才显示；列表没有逐条网络请求。
- 若慢的是点击结果后打开：跨工作区路径会先加载该工作区记住的页面，再加载真正命中页，
  属于另一条串行等待，不能与列表搜索混为一谈。

## 结论与下一步

当前证据偏向 Mica 服务端/主机工作集的偶发抖动，网络及桌面固定等待会叠加，
没有依据将十几秒等待主要归为网络距离。也没有依据声称全部尖峰已经归因于 Swap。

若继续优化，优先在 Mica 搜索中按刷新排队、刷新 SQL、内存扫描、结果 SQL、摘要、
响应传输与桌面可见时间分段测量，并关联进程缺页 / I/O；补慢请求观测后再确定资源或代码改动。
前端取消过期请求，以及跨工作区点击避免先 bootstrap 无关页面，是已识别的独立候选，尚未修改。
不因此修改同机其它项目、机房采集或 VPN。

## 后续（2026-10-19）

两处与"首次搜索新内容慢"直接相关的问题已修（`ff180c2`、`97745a8`）：

- **按查询词变化的那段冷读**：结果 SQL 曾 LEFT JOIN `document_yrs_base` 取每个命中的整篇
  `content_text`，只为切摘要。上表 50 条结果比 0 条多出的 0.1–0.2 s 就在这里，而且命中随查询词
  变化 —— 新词的命中正文不在缓存里，同一个词再搜就快。实测（3000 篇 × 30 KB，重启 PG + 清 OS
  缓存）一次查询读 253 页，去掉后为 0。摘要改从已常驻内存、与匹配同次刷新的 BodyIndex 取。
- **进程内分段观测**：超过 500 ms 的搜索记 `slow search` 警告，带 refresh / scan / sql / 总耗时
  （累计毫秒）与候选数、行数。下次再出现十几秒的尖峰，日志会直接说在哪一段。

未做：前端取消过期请求、跨工作区点击先 bootstrap 无关页面（上文"独立候选"）；BodyIndex 刷新探针
仍是 heap 顺序扫描（给 `updated_at` 建索引会让每次 push 失去 HOT 更新，写放大不划算）。
